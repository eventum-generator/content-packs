# 1C:Enterprise event log generator

Synthetic 1C:Enterprise **event log** records in ECS-compatible JSON for SIEM detections. The generator models one infobase and its users. It does not model the separate technological log.

The `one_c.event_log` object maps the fields of a 1C XML event-log export into snake_case. `event.*`, `user.*`, `host.*` and `related.*` are the normalized SIEM view. The output is JSON, not a native XML export; use a real XML export to test an XML parser.

## Event types

Counts below come from a 14,640-event sample run. The routine state picks Access, Authentication, AccessDenied and User.Update with relative weights `870:120:9:1`. A complete anomaly sequence starts after the first 20 routine records and recurs once per 400 routine records. These are illustrative workload settings, not vendor-published production frequencies.

| Event name | Count | Share | ECS category |
|---|---:|---:|---|
| `_$Access$_.Access` | 12,546 | 85.7% | `database` |
| `_$Session$_.Authentication` | 1,735 | 11.9% | `authentication` |
| `_$Session$_.AuthenticationError` | 140 | 1.0% | `authentication` |
| `_$Access$_.AccessDenied` | 102 | 0.7% | `database` |
| `_$InfoBase$_.EventLogSettingsUpdate` | 35 | 0.2% | `configuration` |
| `_$InfoBase$_.EventLogReduce` | 35 | 0.2% | `configuration` |
| `_$User$_.New` | 35 | 0.2% | `iam` |
| `_$User$_.Update` | 12 | 0.1% | `iam` |

Eight event names are generated by one reusable Jinja template. The template plugin uses **FSM** picking. Routine events draw from five staff accounts and four application objects. Access and access-denied records assume these metadata objects have event-log access auditing enabled. User IDs and sessions stay stable across routine activity; a new authentication advances that user's session number. The generator keeps one source server and infobase throughout.

## Anomaly Chain

Each sequence is ordered and uses the same unmanaged workstation name:

1. Four failed authentications for `admin01`, then a successful one from `UNMANAGED-WS-01`.
2. The administrator creates a new `svc_audit_NNN` user with a `FullAccess` role. That account authenticates from the same workstation.
3. The new account reads `InformationRegisters.PayrollAccruals` twelve times in one session, with different synthetic employee references.
4. The administrator changes event-log settings and reduces the log in the administrator session.

Set `anomaly_mode: false` under `event.template.params` to disable the whole sequence while retaining routine access, authentication, access-denied and user-update events.

The sequence supports separate rules for password guessing, creation of a privileged user, unusual access to payroll data, and log-management activity after those actions. The `FullAccess` role and payroll register belong to the synthetic example configuration; role names and metadata objects vary by deployed 1C solution. Each sequence gets a distinct account name and session numbers. Only the last 1C event-log field values are modeled; the generator does not claim that a log reduction removed the just-generated entries.

## Field mapping

The reference is the [1C:Enterprise Administrator Guide, Appendix 2](https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/1C_Enterprise_8.3.22_Administrator_Guide/Appendix_2._Description_of_the_event_log_items/?language=en), which documents the XML `Event` elements. All 23 documented event fields are emitted under `one_c.event_log`. Blank strings represent fields that do not apply to a particular event; the `Data` field is arbitrary in 1C and is modeled here as a JSON object.

| XML field | JSON field | Generation |
|---|---|---|
| `Level` | `level` | Information or Warning by action |
| `Date` | `date` | Event timestamp |
| `Application` | `application` | Enterprise |
| `ApplicationPresentation` | `application_presentation` | 1C:Enterprise |
| `EventName` | `event_name` | Documented system event name |
| `EventPresentation` | `event_presentation` | Russian presentation of the action |
| `UserID` | `user_id` | Fixed synthetic UUID per actor |
| `UserName` | `user_name` | Synthetic actor account |
| `Computer` | `computer` | Actor workstation |
| `MetadataName` | `metadata_name` | Sample configuration object for access events |
| `MetadataPresentation` | `metadata_presentation` | Object display name |
| `Comment` | `comment` | Action-specific comment or empty |
| `Data` | `data` | Action-specific synthetic structure |
| `DataPresentation` | `data_presentation` | Human-readable action data |
| `TransactionStatus` | `transaction_status` | NotApplicable for modeled actions |
| `TransactionID` | `transaction_id` | Empty for modeled actions |
| `Connection` | `connection` | Stable per session |
| `Session` | `session` | Stable per session |
| `ServerName` | `server_name` | Configured 1C server |
| `Port` | `port` | Configured server port |
| `SyncPort` | `sync_port` | Configured auxiliary port |
| `SessionDataSeparation` | `session_data_separation` | Empty object in this single-area example |
| `SessionDataSeparationPresentation` | `session_data_separation_presentation` | Empty list in this single-area example |

No 1C package with `sample_event.json` and `fields.yml` was found in [Elastic integrations](https://github.com/elastic/integrations). Coverage is measured against the official XML field list instead: **23/23 fields**.

## Parameters

### Event Parameters

Edit `event.template.params` in `generator.yml`:

| Parameter | Default | Purpose |
|---|---|---|
| `infobase` | `AccountingDemo` | Infobase name in `service.name` |
| `server_name` | `srvr-1c-01.example.test` | 1C event-log ServerName |
| `host_name` | `srvr-1c-01.example.test` | Collector host name |
| `server_port` | `1541` | Main 1C server port |
| `sync_port` | `1542` | Auxiliary 1C server port |
| `ecs_version` | `8.11.0` | ECS version |
| `anomaly_mode` | `true` | Enable the complete anomalous sequence; `false` emits background events only |

Edit `samples/actors.json` and `samples/objects.json` for other synthetic users and metadata. Keep user IDs, names and workstation names internally consistent.

### Output Parameters

The shipped file output needs no top-level `${params.*}` or `${secrets.*}` values. To send events to OpenSearch, replace the `output` section with an output plugin and use the following substitution pattern:

```yaml
output:
  - opensearch:
      hosts:
        - ${params.opensearch_host}
      username: ${params.opensearch_user}
      password: ${secrets.opensearch_password}
      index: ${params.opensearch_index}
```

| Placeholder | Purpose |
|---|---|
| `${params.opensearch_host}` | Backend URL |
| `${params.opensearch_user}` | Backend user |
| `${secrets.opensearch_password}` | Keyring-resolved password |
| `${params.opensearch_index}` | Target index |

Supply regular values with `--params` or `startup.yml` and the secret through the Eventum keyring. These overrides are not needed by the shipped `generator.yml`.

## Usage

Run from the `content-packs` repository root with Eventum installed:

```bash
# Continuous stream at about 12 records per second
eventum generate --path generators/application-1c/generator.yml --id one-c --live-mode true

# Fast local sample, stopped after two seconds
timeout 2 eventum generate --path generators/application-1c/generator.yml --id one-c-sample --live-mode false
```

Output is written to `generators/application-1c/output/events.json`. Sample mode runs as fast as possible, so use a short timeout. Exit status 124 means `timeout` stopped a successful run.
